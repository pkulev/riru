#+TITLE: riru

Home overlay for development, patches and live ebuilds.

[[https://github.com/pkulev/riru/actions/workflows/ci.yml][https://github.com/pkulev/riru/actions/workflows/ci.yml/badge.svg?branch=master]]

* Installation
  #+begin_src bash
    $ sudo eselect repository enable riru
    $ sudo emaint sync -r riru
  #+end_src

  We rarely add something that could interfere with your system like programming languages and
  system libraries, so it's safe to leave it like that. But if you want to be extra sure:
  - mask all packages from the overlay (=/etc/portage/package.mask/repo-riru=)
    #+begin_src conf
      ,*/*::riru
    #+end_src

  - and unmask (=/etc/portage/package.unmask/repo-riru=) only those you are interested in:
    #+begin_src conf
      category/package-name::riru
    #+end_src

* How to contribute
** Useful links
   - [[https://devmanual.gentoo.org/][Gentoo developer documentation]]
   - [[https://dev.gentoo.org/~mgorny/articles/the-ultimate-guide-to-eapi-7.html][The ultimate guide to EAPI 7]]
   - [[https://mgorny.pl/articles/the-ultimate-guide-to-eapi-8.html][The ultimate guide to EAPI 8]]
   - [[https://devmanual.gentoo.org/eclass-reference/ebuild/index.html][ebuild file format manual]] or =man 5 ebuild=

** Bump version for existing ebuild
   Let's bump version of =dev-lang/hy= from =1.1.0= to =1.3.0= version.
   #+begin_src bash
     $ cd dev-lang/hy
     $ cp hy-1.1.0.ebuild hy-1.3.0.ebuild
     $ ebuild hy-1.3.0.ebuild manifest
     $ git add hy-1.3.0.ebuild Manifest
     $ git commit -s -m "dev-lang/hy: bump version to 1.3.0"
   #+end_src

** Adding new ebuilds
   It's encouraged to use newest EAPI version possible, but you can use any EAPI
   that greater or equals to that written at =profiles/eapi= of this overlay.

   After adding or bumping ebuilds, refresh packages list in this README:

   #+begin_src bash
     $ bb readme:packages
   #+end_src

** Continuous integration
   CI runs on every push and pull request to =master= (see
   [[https://github.com/pkulev/riru/actions/workflows/ci.yml][.github/workflows/ci.yml]]):

   - =bb readme:packages:check= — package table in this README matches ebuilds
   - =pkgcheck= — ebuild QA (with =--net= distfile fetch checks)

   Run the same checks locally before pushing:

   #+begin_src bash
     $ bb ci:check
   #+end_src

** Version bumps
   Open a [[https://github.com/pkulev/riru/issues/new?template=version_bump.yml][version bump issue]]
   or run the [[https://github.com/pkulev/riru/actions/workflows/bump.yml][Version bump]]
   workflow manually. CI opens a pull request; old ebuild versions are kept and
   merging stays manual. Manifests are regenerated with =pkgdev manifest= when distfiles are available.

   Locally:

   #+begin_src bash
     $ bb bump:version --pkg-atom dev-lang/hy --version 1.4.0
   #+end_src

   After ebuild changes, refresh the package table with =bb readme:packages=.

*** Rust packages (crate tarball)
    Cargo ebuilds use =CRATES=""= and fetch =${P}-crates.tar.xz= from the fixed
    [[https://github.com/pkulev/riru/releases/tag/1.0.0][riru 1.0.0]] release.
    After the version-bump PR opens (Manifest often fails until crates exist):

    1. Upload crates locally (skip Manifest; CI will refresh it):
       #+begin_src bash
         $ bb bump:crates --pkg-atom games-util/open-steam-controller --version 1.2.0 --skip-manifest
       #+end_src
    2. Add the =deps-uploaded= label on the PR. CI runs
       [[https://github.com/pkulev/riru/actions/workflows/bump-manifest.yml][Refresh bump Manifest]]
       and pushes the updated Manifest.

    Needs =pycargoebuild=, =pkgdev=, and =gh=. Other flags: =--dry-run=, =--skip-upload=.

*** Chicken eggs (source tarball)
    =dev-chicken/*= eggs fetch =${CHICKEN_EGG}-${PV}.tar.xz= from the same
    [[https://github.com/pkulev/riru/releases/tag/1.0.0][riru 1.0.0]] release
    (Portage fetch phase; see =chicken-egg.eclass=). Refresh mirrors with:

    #+begin_src bash
      $ bb bump:eggs --from-henrietta
      $ bb bump:eggs --pkg-atom dev-chicken/srfi1 --version 0.5.1 --from-henrietta
    #+end_src

    Prefer =--from-henrietta= for release uploads (clean sources, including
    predefined =.types= files). Otherwise: overlay =files/= -> chicken cache
    (build leftovers are scrubbed). Needs =pkgdev= and =gh=. Flags:
    =--dry-run=, =--skip-upload=, =--skip-manifest=.

** Local ebuild testing
   You can test ebuilds against this overlay from the repo root. Portage scratch
   directories (=.portage*=) are gitignored and safe to leave in the tree.

   #+begin_src bash
     $ PORTDIR_OVERLAY=$PWD DISTDIR=$PWD/distdir \
       ebuild path/to/foo-version.ebuild clean install
     # staged image: .portage-tmp/portage/category/foo-version/image/
   #+end_src

   Or a full emerge dry-run against the overlay:

   #+begin_src bash
     $ PORTDIR_OVERLAY=$PWD emerge -pv =category/foo-version::riru
   #+end_src

** Creating requests for writing ebuilds
   You also can create issue with detailed information about package you want see
   in Gentoo. It's totally not guaranteed that it will be done, but who knows.
   Issues are free to create so why not?

** Refactor existing ebuilds
   You can change existing ebuilds to add new functionality, solve QA issues or
   bump EAPI version.
